# StarTunnel v0.4.3

This release repairs replacement-host database recovery and PostgreSQL password
rotation. It also fixes readiness checks for production containers and prevents
the browser from displaying expired cycle content.

## Install or upgrade

Use the [tagged installation guide](https://github.com/btfranklin/startunnel/blob/v0.4.3/docs/setup/README.md)
or the [tagged update guide](https://github.com/btfranklin/startunnel/blob/v0.4.3/docs/setup/maintain.md#update-the-application).
Download the attached `release.json` and use its immutable application image.
Host tools require Python 3.15.2 or later.

The supported direct upgrade sources are v0.2.0, v0.3.0, v0.4.0, v0.4.1, and
v0.4.2. For v0.1.0 and older installations, start with the
[tagged v0.2.0 guide](https://github.com/btfranklin/startunnel/blob/v0.2.0/docs/setup/maintain.md#update-the-application).
When upgrading from v0.2.0 or v0.3.0, also follow the v0.4.0 credential-cap and
trusted-proxy instructions.

Before the update, make and restore-check a fresh off-server backup. Upgrade
preview checks for admin usernames that differ only in case. If it finds a
conflict, give each affected account a distinct name on the installed release
and run preview again. Migration `accounts.0005` enforces this rule in the
database. PostgreSQL remains on major version 18.

After the server update, run `startunnel update` on each client from the upgraded
instance. Verify an existing agent credential or admin credential. The minimum
official CLI version remains v0.3.0.

## Fixes

- Replacement-host recovery restores into an empty database, checks its data
  and runtime role, then switches database names in one transaction.
- Password rotation uses the mounted secrets for its readiness check. If the
  database does not confirm the change, rotation checks which credentials work
  before it reports the outcome or attempts rollback.
- Production startup and upgrade check the effective Compose configuration.
  Upgrades pull enabled images before stopping writers. Backups and maintenance
  share an instance lock.
- Container readiness works when the public endpoint requires HTTPS. Admin
  username checks and database writes use the same case-insensitive rule.
- Release evidence identifies each tested upgrade source. CI starts service
  checks after source security clears and preserves the Chromium, Firefox, and
  WebKit suite with a smaller helper image.

## Recovery

Keep the verified database backup with the previous source, image references,
configuration, and secrets. If recovery is necessary after a migrated upgrade,
stop writers and restore those inputs together. A database restore removes
writes made after the backup. Use the
[replacement-host recovery instructions](https://github.com/btfranklin/startunnel/blob/v0.4.3/docs/setup/backups.md#recover-on-a-replacement-server)
and verify an existing agent credential before resuming service.
