# StarTunnel v0.3.0

The CLI can now check its selected configuration without a network request. It
can read an agent key from a private file. Its offline command definitions now
include generated API responses, successful CLI output, and error output.
`startunnel version` also shows the executable path to help find installed copies.

The server requires official CLI v0.3.0 or later. An old official CLI receives
a clear update error before an API operation runs. Update each client after
the server update. Updates remain explicit; commands do not replace the client
automatically.

## Update an existing instance

1. Read the [v0.3.0 server update guide](https://github.com/btfranklin/startunnel/blob/v0.3.0/docs/setup/maintain.md#update-the-application).
   Download the attached `release.json`. It supplies the exact source commit
   and immutable Linux amd64 image digest. The supported published predecessor
   is v0.2.0. For v0.1.0 or older installations, first follow the
   [tagged v0.2.0 update guide](https://github.com/btfranklin/startunnel/blob/v0.2.0/docs/setup/maintain.md#update-the-application).
2. Make a fresh backup, test its restore, and keep the backup and recovery
   secrets outside the server. Keep the old image and source checkout. Plan a
   maintenance window.
3. Check out the source commit from `release.json`. Load the existing
   production configuration. Run the upgrade helper's preview, then apply it
   with `--apply --backup-verified`. This release has no database migration or
   server environment change. The preview and apply still check the release
   record, source, image, backup, and selected database.
4. Update the CLI on **each agent and administrator host**, including copies in
   agent images and jobs. Set `STARTUNNEL_BASE_URL` to the upgraded instance,
   then run `startunnel update`, `startunnel version`, and `startunnel config`.
   Run `startunnel me` to verify agent access. Admin users run
   `startunnel admin config` and `startunnel admin me`. Existing keys remain valid. Make a new backup after
   external checks pass.

The complete commands are in the
[v0.3.0 server guide](https://github.com/btfranklin/startunnel/blob/v0.3.0/docs/setup/maintain.md#update-the-application).
New installations can start with the
[v0.3.0 setup index](https://github.com/btfranklin/startunnel/blob/v0.3.0/docs/setup/README.md).

## CLI configuration and response help

Agent commands can use `STARTUNNEL_AGENT_KEY_FILE` instead of
`STARTUNNEL_AGENT_KEY`. Set exactly one. The key file must be readable and
contain one key. Keep it in a private directory. Use mode `0600` on Linux or
macOS. Admin commands support the corresponding admin key-file setting.
No server setting is required.

Run `startunnel config` to check the selected origin and credential source
offline. This does not prove server access or key validity. Run `startunnel me`
for that network check. Admin users use `startunnel admin config` and
`startunnel admin me`.

Run `startunnel schema` or `startunnel admin schema` for offline command
definitions. They include API response definitions, successful CLI output, and
the CLI error format. These definitions describe the client build; they do not
verify a remote server. The updated client is required for the new output.

## CLI version check

The server returns its version, minimum CLI version, and reported client
compatibility in API response headers. Missing versions from old official
clients, old release versions, and invalid version labels return HTTP `400`
with `invalid_request`. Existing v0.2.0 clients can display the update message.
The download path remains available, so `startunnel update` still works.

Source builds send `unreleased` and remain unverified. Other API clients can
omit the version header. Version reporting is not authentication; normal
credential and access checks still apply. See the
[v0.3.0 API guide](https://github.com/btfranklin/startunnel/blob/v0.3.0/docs/api.md).

## Rollback

Restore the v0.2.0 source and image with the existing configuration. This
release does not change the database schema or data. Keep the verified backup,
prior source checkout, image, configuration snapshots, and secret files until
the upgraded instance passes external checks. Once the server is restored,
clients can explicitly run `startunnel update` from that instance. The v0.2.0
client does not have the new configuration and response-definition features.
