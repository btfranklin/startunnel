# StarTunnel v0.4.1

This release updates the application and host tools to Python 3.15, refreshes
locked dependencies, and adds strict type checks for all Python source files.
It also reduces release helper build cost, records safe load measurements, and
keeps explicit proof attempts and timing records for release validation.

## Update an existing instance

1. Read the [v0.4.1 server update guide](https://github.com/btfranklin/startunnel/blob/v0.4.1/docs/setup/maintain.md#update-the-application).
   Download the attached `release.json`. Use its exact source commit and Linux
   amd64 image digest. Supported published predecessors are v0.2.0, v0.3.0,
   and v0.4.0. Older installations must first follow the
   [tagged v0.2.0 guide](https://github.com/btfranklin/startunnel/blob/v0.2.0/docs/setup/maintain.md#update-the-application).
2. Install Python 3.15 or later on the host before running the upgrade tools.
   The official application image includes its Python runtime. Make a fresh
   backup, test its restore, and keep the old source, image, configuration,
   secrets, and backup outside the server.
3. Check out the source commit from `release.json`. Load the existing production
   configuration. Preview the upgrade, then apply it with
   `--apply --backup-verified` after the backup checks. There are no new
   migrations after v0.4.0. Data and credentials are preserved.
4. Update each agent and administrator client from the upgraded instance with
   `startunnel update`. Run `startunnel version`, `startunnel config`, and
   `startunnel me`. Administrators run `startunnel admin config` and
   `startunnel admin me`. These commands confirm authentication with the
   existing keys. The minimum official CLI remains v0.3.0; the standalone CLI
   still supports Python 3.10 or later. This release requires no new CLI command
   or request field.
5. Repeat external administrator and two-agent checks, inspect operation
   receipts and audit records, and make a new backup after verification.

Upgrades from v0.2.0 or v0.3.0 must also apply the
[v0.4.0 credential-cap and proxy instructions](https://github.com/btfranklin/startunnel/blob/v0.4.0/releases/v0.4.0.md).
Those upgrades apply `tunnels.0011`, which has no reverse operation. Re-create
the included Caddy service and check explicit trusted-proxy settings as directed.

New installations can use the
[v0.4.1 setup index](https://github.com/btfranklin/startunnel/blob/v0.4.1/docs/setup/README.md).
Publication does not update an installed instance.

## Runtime and validation changes

The application uses Python 3.15 and updated locked dependencies. Middleware
uses scoped request context. The load driver uses scoped async tasks. Strict
type checks cover application code, migrations, tests, scripts, and examples.

Release load helpers contain only the production dependencies and proof source
they need. Scoped BuildKit caches reduce repeated dependency work. Each helper
still builds from and verifies the current source. Candidate identity is checked
before expensive proof work and again at completion.

Load reports include safe numeric resource, database-pool, scheduling, and
collector measurements. Transport failures retain public exception classes
without exception text or request data. Client test connections expire before
the server's idle-close boundary. Load acceptance limits are unchanged, and
transport failures still fail the proof. Pool sampling remains disabled outside
proof runs.

Proof artifacts retain run and attempt identities, file checksums, cleanup
results, and failed attempts. Release status reports show source CI, candidate
identity, selected evidence, cache results, and elapsed time. A controlled lock
diagnostic cannot be used to promote a release.

## Rollback

Keep the previous source, immutable image, configuration, secrets, and verified
pre-upgrade database backup until external checks pass. If recovery is required,
stop writers and restore these matching inputs together. Recovery loses writes
made after the backup. Do not reverse `tunnels.0011` or use a pre-v0.4.0 image
against its migrated database. See
[backup recovery](https://github.com/btfranklin/startunnel/blob/v0.4.1/docs/setup/backups.md#recover-on-a-replacement-server).
