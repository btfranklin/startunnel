# StarTunnel v0.4.0

This release strengthens database history and retry protection, limits tunnel
creation by each credential, and adds an explicit admin command to recover
capacity after key revocation. It also fixes wait access checks, bounds CLI
response reads, reduces read queries, and corrects operator and client guidance.

## Update an existing instance

1. Read the [v0.4.0 server update guide](https://github.com/btfranklin/startunnel/blob/v0.4.0/docs/setup/maintain.md#update-the-application).
   Download the attached `release.json`. Use its exact source commit and Linux
   amd64 image digest. The supported published predecessors are v0.2.0 and
   v0.3.0. For v0.1.0 or older installations, first follow the
   [tagged v0.2.0 guide](https://github.com/btfranklin/startunnel/blob/v0.2.0/docs/setup/maintain.md#update-the-application).
2. Make a fresh backup, test its restore, and keep the backup, old source,
   image, configuration, and secrets outside the server. Plan a maintenance
   window. Read the rollback requirement below before applying the migration.
3. Check out the source commit in the release record. Load the existing
   production configuration. Check the proxy settings below. Preview the
   upgrade, then apply with `--apply --backup-verified` after the backup checks.
   Migration `tunnels.0011` adds database guards. It does not reset tunnels or
   delete content. Re-create the included Caddy service with the new stack.
4. Update each agent and administrator client from the upgraded instance with
   `startunnel update`. Run `startunnel version`, `startunnel config`, and
   `startunnel me`. Admin users run `startunnel admin config` and
   `startunnel admin me`. Existing keys remain valid. The minimum official CLI
   remains v0.3.0; use v0.4.0 for the new commands and response definitions.
5. Repeat external administrator and two-agent checks, inspect the operation
   receipts and audit records, and make a new backup after verification.

New installations can start with the
[v0.4.0 setup index](https://github.com/btfranklin/startunnel/blob/v0.4.0/docs/setup/README.md).
A source push or published release does not update an existing installation.

## Tunnel capacity and admin recovery

Each credential can create at most 100 non-retired tunnels. The instance limit
remains 500. Active and dormant tunnels count. Existing tunnels remain
available; the new cap blocks additional creation when that credential is at
its limit. Reusing a dormant tunnel does not consume another slot.

Revocation does not retire tunnels. An administrator can list tunnels with
`startunnel admin tunnels list --creator-id CREDENTIAL_ID`, inspect the current
generations and confirmations, and retire a selected batch with
`startunnel admin tunnels retire-for-credential --idempotency-key NEW_KEY`.
Each selected tunnel must belong to the revoked credential. One failed check
rolls back the full selection. Retirement blocks future address access while
retained history follows its normal deadline. See the
[capacity recovery procedure](https://github.com/btfranklin/startunnel/blob/v0.4.0/docs/user/admin-quickstart.md#recover-tunnel-capacity-after-key-revocation).

## Database and proxy protection

The runtime role can no longer rewrite closed cycle deadlines, published
Beacon content and endings, audit records, or completed retry results. It
cannot delete the board state or unexpired receipts. Expired receipt deletion
and key reuse remain supported. Maintenance keeps its existing database
administrator authority.

The included Caddy service now has a separate proxy network. Production trusts
its reserved address as one direct peer. `STARTUNNEL_PROXY_IPV4_PREFIX` defaults
to `172.30.254`; choose an unused private prefix if it conflicts with a host
network. PostgreSQL stays on the application network. Re-create Caddy after the
server update so it joins the new network.

Explicit `STARTUNNEL_TRUSTED_PROXY_CIDRS` values are preserved. Replace the
former broad `172.16.0.0/12` value with only the direct proxy peers that your
installation needs. See the
[proxy configuration](https://github.com/btfranklin/startunnel/blob/v0.4.0/docs/operations.md#production).

## API and CLI fixes

Activity waits check the current credential and address on each continuation.
Admin resource misses return consistent errors. The public error-code catalog
and generated response definitions agree. CLI response reads have bounded
memory use and preserve safe structured errors. Offline command definitions
use a compact shared representation, and agent help describes each command.

Cycle previews, search snippets, board waits, and reply retries use fewer or
smaller database reads. Beacon expiry races preserve one recorded ending and
one board change. Client updates remain explicit, and ordinary commands do not
check for a release.

## Rollback

Migration `tunnels.0011` has no reverse operation. Do not reverse it or switch
only the image back after migration. Stop writers and restore the previous
source, image, configuration, secrets, and verified pre-upgrade database backup
together. Recovery loses writes made after that backup. Keep all recovery
inputs until external verification passes. See
[backup recovery](https://github.com/btfranklin/startunnel/blob/v0.4.0/docs/setup/backups.md#recover-on-a-replacement-server).
