# StarTunnel v0.1.0

First versioned distribution of StarTunnel, with an official Linux amd64 runtime
image and an immutable deployment record. Includes agent-first administration through the existing CLI and a typed admin
API, optional browser passwords, named admin keys, operation receipts, and audit
inspection. The browser remains available for manual administration.

## Administration and documentation fixes

The interface and API notice now say: **Tunnels should not be treated as
confidential.** Tunnel descriptions no longer use the former unlisted-access
wording. The access rules remain unchanged.

The setup guides now lead with key-only administration and show browser-password
setup as a separate interactive choice. They distinguish container and client
key files, explain recovery, and require identity, health, receipt, and audit
verification. The admin quickstart covers account, key, and tunnel controls,
exact retries, private output files, and the full unattended acceptance sequence.

The existing CLI's `admin schema` now points to the running instance's correct
OpenAPI path, `/api/v1/openapi.json`. Agent guides, public documentation, and
website references use the same administration workflow.

## Installation and upgrades

Use `release.json` attached to this release for the exact source commit and
image digest. Follow the repository installation and maintenance guides.
There are no new configuration settings for this release.

This is the first supported database baseline. An existing unversioned instance
can upgrade only if its recorded source commit is an ancestor of this release
and its applied migration files match the unchanged initial prefix. Additive
forward migrations preserve accounts, passwords, agent keys, messages, and old
audit records. A restored-database upgrade and recovery test must prove the
exact installed source before compatibility is claimed. No published predecessor
is listed. Other migration graphs need a separately reviewed conversion.

The local restored-baseline proof passed using synthetic data on the matching
pre-change initial migrations. It preserved account and message IDs, passwords,
agent authentication, message ancestry, and historical audit records. It also
proved server key recovery and new writes after migration. This is not a restored
production snapshot or evidence for a published predecessor. `supported_from`
remains empty. Use `pdm run python scripts/prove_admin_upgrade.py` to repeat it.

Back up and test recovery before upgrading. Keep the previous image and source
commit. Rollback after a database change requires the corresponding database
backup and secrets, rather than just the old image.

## Administrator access

Use `create_instance_admin NAME --key-file FILE` for a key-only first admin, or
retain the interactive password flow. Use `recover_instance_admin NAME --key-file
FILE` on the server if remote access is lost. Files must remain private. Admin
keys use `sta_`; message keys use `st_`. The two key types have separate access.

Deactivation revokes the account's admin keys. Reactivation requires new keys.
The service protects the last usable and non-expiring admin recovery path.
Deployment, backup, restore, and upgrades remain server operations.
